## 기본

### 단일 인스턴스 환경에서 굳이 도입한 이유

단일 EC2 환경이었기 때문에 부하 분산보다는 인프라와 애플리케이션의 책임 분리를 목적으로 Nginx를 도입했습니다.  
TLS 처리와 인증서 관리, 운영 Swagger에 대한 접근 제어를 Nginx에서 담당하도록 구성했습니다.  
Spring Boot에서도 이러한 기능을 구현할 수 있지만, Nginx에 위임함으로써 인프라 운영 정책이 변경되더라도 애플리케이션의 코드 수정이나 재배포, 재시작 없이 독립적으로 관리할 수 있도록 설계했습니다.


## 인증 흐름

1. 프론트가 `/api/v1/auth/oauth2/{provider}`로 이동합니다.
2. Spring Security가 provider 인증을 진행하고, 백엔드 callback에서 authorization code를 토큰으로 교환합니다.
3. `OAuth2LoginService`가 provider 사용자 정보를 해석해 기존 회원을 찾거나 신규 회원을 만듭니다.
4. Matchuri 자체 Refresh Token과 단기 교환 코드를 발급합니다.
5. Refresh Token은 HttpOnly 쿠키에 넣고, 프론트에는 교환 코드만 전달합니다.
6. 프론트가 `/api/v1/auth/oauth2/exchange`를 호출해 Matchuri Access Token을 받습니다.


# 포트폴리오

## 재처리 로직

### AES 암호화 알고리즘에 대해 설명해주세요

[[AES]]는 128bit 크기의 고정된 블록을 암호화하는 대칭키 알고리즘이며, 운용 모드는 이러한 블록 암호를 실제 데이터에 적용하는 방식을 정의한다. 운용 모드에는 ECB, CBC, CTR, GCM 등이 존재하며 각각 블록 처리 방식, 초기화 벡터 사용, 패딩 및 무결성 검증 여부에서 차이가 있다. 특히 GCM은 데이터의 기밀성과 무결성을 함께 제공하는 인증 암호화 방식으로, 새로운 애플리케이션 개발에서 일반적으로 권장된다. 단, 동일한 키에서 Nonce를 재사용하지 않도록 주의해야 한다.

## JPA N+1 문제 해결 및 조회 쿼리 최적화

JPA의 지연 로딩으로 인해 데이터 규모에 따라 SQL 실행 횟수가 증가하는 문제를 분석하고, QueryDSL 기반 조회 구조로 개선했습니다.

- QueryDSL의 Scalar Projection을 활용해 필요한 데이터만 조회하고, 다중 컬렉션 조인으로 인한 카테시안 곱을 방지하도록 조회 쿼리를 분리했습니다.
- 메뉴 상세 조회 28회 → 3회, 비회원 추천 20회 → 7회, 그룹 상세 조회 15회 → 8회로 SELECT 실행 횟수를 줄이고 통합 테스트로 검증했습니다.

## OAuth2 임시 상태와 API 인증 분리

OAuth2 요청 객체 전체를 쿠키로 전달하던 방식을 바꾸고, 로그인 시작과 콜백 사이의 임시 상태만 세션에 저장하도록 구성했습니다.

- `HttpSessionOAuth2AuthorizationRequestRepository`에 요청 상태 저장을 위임했습니다.
- 콜백 처리 후 임시 Authorization Request를 제거했습니다.
- API의 JWT Access Token·Refresh Token 인증 흐름은 유지했습니다.

## OIDC·SSM 기반 배포 구성

GitHub Actions의 장기 PEM 키와 직접 SSH 접속 의존을 줄이기 위해, 기존 JAR·systemd 배포 절차에 OIDC와 SSM Run Command를 연결했습니다.

- Actions는 OIDC 임시 권한을 사용하고, 빌드한 JAR는 S3로 전달했습니다.
- EC2는 SSM 명령으로 산출물을 받아 기존 배포 스크립트를 실행하도록 구성했습니다.
- SSM 실행 상태와 EC2 내부 health check를 확인해 빌드 완료와 애플리케이션 기동을 구분했습니다.
