락은 상태 변경 과정의 동시성을 제어하는 수단이지, 모든 데이터 정합성 문제의 근본적인 해결책은 아니라고 생각합니다.

특히 현재 구현을 다시 분석해 보니 게시글에 직접 락을 거는 방식은 서로 다른 사용자들의 독립적인 찜 요청까지 직렬화하는 문제가 있었습니다.

또한 사용자 찜하기처럼 찜 레코드 자체에 락을 거는 경우에는 최초 생성 시점에 잠글 레코드가 존재하지 않는 문제도 있었습니다.

따라서 중복 데이터는 DB 유니크 제약조건으로 보장하고, 상태 변경은 UPSERT와 같은 원자적 연산으로 처리하는 방식을 개선안으로 고려하고 있습니다. 나아가 중복 요청에 대한 사용자 의도를 보장하기 위해 토글 API를 명시적 상태 설정 API로 분리하는 것도 검토할 수 있다고 생각합니다.
