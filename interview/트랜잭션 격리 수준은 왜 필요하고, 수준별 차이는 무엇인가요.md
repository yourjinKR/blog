트랜잭션 [[Isolation Level|격리 수준]]은 여러 트랜잭션이 동시에 실행될 때 어느 정도까지 서로의 변경을 볼 수 있게 할지 정하는 기준입니다. 격리를 강하게 하면 데이터 일관성은 높아지지만 잠금 대기나 충돌이 늘어 동시성과 처리량이 낮아질 수 있어, 업무에서 허용할 수 있는 [[Anomaly|이상 현상]]과 성능을 함께 고려해야 합니다.  

실무에서는 성능을 위해 주로 `READ COMMITTED`를 주로 사용하며, 정산처럼 일과성이 중요한 경우 `REPEATABLE READ` 기반에 [[Lock#Pessimistic Lock|비관적 락]]을 조합하여 필요한 행만 명시적으로 잠그는 전략을 선택합니다.   

| 격리 수준              | 특징                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `READ UNCOMMITTED` | 커밋되지 않은 변경도 읽을 수 있어 Dirty Read가 발생할 수 있습니다.                                                        |
| `READ COMMITTED`   | 커밋된 데이터만 읽지만, 조회할 때마다 새 스냅샷을 사용하므로 Non-Repeatable Read와 Phantom Read가 발생할 수 있습니다.                  |
| `REPEATABLE READ`  | 같은 트랜잭션의 일반 조회는 동일한 스냅샷을 사용하여 반복 조회 결과를 안정적으로 유지합니다. SQL 표준상 Phantom Read가 가능하지만 구현체에 따라 동작이 다릅니다. |
| `SERIALIZABLE`     | 트랜잭션을 순차적으로 실행한 것과 같은 수준의 격리를 제공하지만 대기와 충돌이 가장 많습니다.                                               |

| 격리 수준              | Dirty Read | Non-Repeatable Read | Phantom Read |
| ------------------ | :--------: | :-----------------: | :----------: |
| `READ UNCOMMITTED` |    ✅ 허용    |        ✅ 허용         |     ✅ 허용     |
| `READ COMMITTED`   |    ❌ 방지    |        ✅ 허용         |     ✅ 허용     |
| `REPEATABLE READ`  |    ❌ 방지    |        ❌ 방지         |    ✅ 허용*     |
| `SERIALIZABLE`     |    ❌ 방지    |        ❌ 방지         |     ❌ 방지     |

MySQL InnoDB의 격리 레벨은 표준에서 정의한 격리 레벨을 사용하며 기본값은 `REPEATABLE READ`입니다. 일반 조회는 [[MVCC]] 스냅샷을 사용하고, 잠금 조회나 범위 수정에서는 Next-Key Lock을 사용해 팬텀을 방지할 수 있습니다.  

Oracle에서 지원하는 Isolation Level은 `REPEATABLE READ`와 `SERIALIZABLE`입니다.    
ORacle의 `SERIALIZABLE`는 [[Snapshot Isolation]]으로 동작합니다.   

SQL Server는 표준 SQL에서 정의한 Isolation Level를 기반으로 정의합니다.  

PostgreSQL는 표준 SQL에서 정의한 Isolation Level를 기반으로 정의합니다.  
PostgreSQL에서는 `REPEATABLE READ`가 Snapshot Isolation으로 동작합니다.  

> [!QUESTION]- Spring에서 격리 수준을 지정하지 않으면 어떤 값이 사용되나요?
> `@Transactional`의 기본값은 `Isolation.DEFAULT`이므로 데이터베이스의 기본 격리 수준을 사용합니다. MySQL InnoDB는 기본적으로 `REPEATABLE READ`를 사용하지만 운영 DB 설정이 다를 수 있으므로 실제 값을 확인해야 합니다.

> [!QUESTION]- 격리 수준을 높이면 Lost Update도 항상 방지되나요?
> 아닙니다. 애플리케이션이 값을 읽고 계산한 뒤 저장하는 Read-Modify-Write 과정에서는 격리 수준만으로 갱신 유실을 완전히 막지 못할 수 있습니다. 원자적 UPDATE, 낙관적 락의 버전 검사, 비관적 락 등 업무에 맞는 동시성 제어가 필요합니다.

> [!QUESTION]- MVCC는 격리성과 동시성을 어떻게 높이나요?
> [[Snapshot Isolation|변경 전 버전을 보관]]하고 트랜잭션의 Read View에 맞는 데이터를 반환하여 일반 조회가 쓰기 잠금을 기다리지 않게 합니다. 읽기와 쓰기의 충돌은 줄지만 과거 버전 관리 비용이 있고, 잠금 조회와 쓰기 작업에는 여전히 잠금이 필요합니다.

> [!QUESTION]- Q1. 왜 Oracle은 READ COMMITTED를, MySQL은 REPEATABLE READ를 기본으로 쓰나요?
> 
> Oracle은 일반적인 트랜잭션에서 동시성과 처리량을 확보하는 것을 중시했고, MySQL InnoDB는 반복 읽기의 일관성을 기본적으로 제공하는 방향을 채택했기 때문입니다.
> 
> - Oracle: ==대부분의 트랜잭션은 동일한 데이터를 반복 조회할 필요가 없다고 판단==했습니다. 따라서 불필요하게 높은 격리 수준을 적용하기보다 `READ COMMITTED`를 통해 동시성과 처리량을 확보하도록 설계했습니다.
>     
> - MySQL InnoDB: MVCC를 통해 일반 SELECT에 별도의 읽기 잠금을 걸지 않으면서도 트랜잭션 내 동일한 스냅샷을 유지할 수 있습니다. 또한 과거 Statement-Based Replication과의 호환성 측면에서도 `REPEATABLE READ`의 잠금 동작이 중요했습니다.
>     
> 
> 즉, Oracle은 일반적인 작업에 충분한 일관성과 높은 동시성을, MySQL은 반복 읽기 일관성을 기본적으로 제공하는 방향을 선택한 것으로 이해할 수 있습니다.

> [!QUESTION]- Q2. REPEATABLE READ에서 Phantom Read가 발생하는 결정적인 이유는?
> 
> SQL 표준에서 REPEATABLE READ는 기존 행의 반복 읽기를 보장하지만, 검색 조건에 해당하는 행 집합의 변화까지 반드시 방지하지는 않기 때문입니다.
> 
> - Non-Repeatable Read: 기존에 조회한 행의 값이 변경되는 문제입니다.
>     
> - Phantom Read: 다른 트랜잭션이 검색 조건에 해당하는 행을 삽입하거나 삭제하여 재조회 시 결과 집합이 달라지는 문제입니다.
>     
> 
> 다만 MySQL InnoDB의 `REPEATABLE READ`는 예외적으로 일반 SELECT에서 Phantom Read를 방지합니다. MVCC의 동일 스냅샷을 사용하기 때문이며, 잠금 읽기에서는 Next-Key Lock과 Gap Lock을 활용해 범위 내 삽입을 제한합니다.
> 
> 따라서 SQL 표준의 격리 수준 정의와 DBMS의 실제 구현을 구분해야 합니다. 특히 InnoDB에서도 일반 SELECT와 잠금 읽기를 혼용할 때는 결과가 달라질 수 있습니다.
> 

> [!QUESTION]- Q3. SELECT FOR UPDATE는 언제 사용해야 하나요?
> 
> 동시 트랜잭션이 동일한 데이터를 변경할 가능성이 있고, 조회한 값을 바탕으로 수정 여부를 판단해야 할 때 사용합니다.
> 
> `SELECT FOR UPDATE`는 조회 대상에 [[Lock#Pessimistic Lock|베타적 잠금]]을 획득하여 다른 트랜잭션이 해당 데이터를 동시에 수정하지 못하도록 제한합니다.
> 
> - 사용 사례: 재고 차감, 잔액 차감 등 현재 값을 조회하고 비즈니스 조건을 검증한 뒤 수정해야 하는 경우입니다.
>     
> - 주의 사항: 잠금으로 인해 대기 시간이나 데드락이 발생할 수 있으므로 필요한 범위에만 적용하고 트랜잭션을 짧게 유지해야 합니다.
>     
> 
> 단순한 원자적 UPDATE나 낙관적 락으로 해결할 수 있다면 반드시 사용할 필요는 없습니다.
