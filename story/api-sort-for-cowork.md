## 개요

팀프로젝트 인원이 모두 개발자라는 점을 고려하여 swagger를 공식 문서로 두고 작업을 진행했다.  

그러나 작업이 진행됨에 따라 수많은 API들이 정의 및 구현되었고  
문서를 읽는 것에 있어서 여러 불편함을 느꼈다.  

- 소통시 특정 API에 대한 `summary`나 `url`로 언급

## swagger-ui 자체 정렬 기능

swagger-ui에서 설정값을 통해 정렬하는 기능이 존재한다.  

```yaml
spring-doc:
  swagger-ui:
    tags-sorter: alpha
    operations-sorter : method
    doc-expansion : none
```

완전히 커스텀 정렬 또한 지원하는지 확인해봤다.

## API 고유 넘버링 도입

이러한 불편사항을 고려하여 다음과 같은 넘버링을 생각했다.

```markdown
- 2.0.0  온보딩/내 정보 플로우
- 2.1.0  필수 약관 상태 조회
- 2.2.0  필수 약관 동의 제출
- 2.3.0  내 취향 프로필 조회
- 2.4.0  내 취향 프로필 저장
...
```

이러한 고유 넘버링을 도입한다면 팀원 간 소통시 편하게 할 수 있을 것이다.

또한 해당 넘버링을 유저 플로우 순서에 맞게 지정한다면  
명세를 봤을 때 다음에 호출할 API들을 직관적으로 확인할 수 있을거라 생각했다.  

요구사항 변경으로 인한 유저 플로우 중간에 별도의 API 삽입해야 한다면 다음과 같은 규칙으로 정렬할 수 있을 것이다.  

```markdown
- 2.0.0  온보딩/내 정보 플로우
- 2.1.0  필수 약관 상태 조회
<!-- - 2.1.5  선택 약관 상태 제출 -->
- 2.2.0  필수 약관 동의 제출
<!-- - 2.2.5  선택 약관 상태 제출 -->
- 2.3.0  내 취향 프로필 조회
- 2.4.0  내 취향 프로필 저장
```

### 도메인에 고유 영문코드 부여

그러나 기존 넘버링 구조는 새로운 도메인이 추가됐을 때는  정렬에 문제가 생긴다.  

```markdown
- 1: 인증/가입
- 2: 온보딩/내정보
<!-- 헤당 위치에 추가 도메인이 요구 -->
- 3: 메뉴/취향 정보
```

이를 고려하여 아래와 같이 고유 영문 코드를 통해 넘버링을 규정했다.

| 코드      | 플로우        |
| ------- | ---------- |
| `OPS`   | 공통/운영      |
| `AUTH`  | 인증/가입      |
| `ONB`   | 온보딩/내 정보   |
| `REF`   | 메뉴/취향 참조   |
| `REC`   | 개인 추천      |
| `GROUP` | 그룹 생성/참여   |
| `GREC`  | 그룹 추천/투표   |
| `ADMIN` | 관리자 데이터 운영 |
