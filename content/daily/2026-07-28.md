## 유지보수

채팅 메세지 전송 로직에서 메세지 성공시 FCM으로 앱 푸시 알람을 보내야 하는 추가 요구사항이 생겼다.  

그 과정에서 메세지를 받는 멤버인 `receiver`를 조회할 필요가 있었다.  
그러나 이전에 채팅방은 웹소켓이기에 메세지를 보내는 과정에서 수신자를 알 필요가 없기에 검증 메서드 안에서 수신자를 조회했다.  

이런 상황에서 `receiver`를 다시 조회하거나 `validateCanSendMessage` 메서드를 리팩토링할 필요가 있었다. 

`sender`가 메세지를 보낼 수 있는 권한을 검사하는 메서드를 만들었다.   

```java
private ChatRoomMember validateCanSendMessage(Long chatRoomId, Long senderId) {  
    ChatRoomMember sender = chatRoomMemberService.findActiveMemberByRoomIdAndMemberId(chatRoomId, senderId);  
    Member opponent = chatRoomMemberService.findPartnerMember(sender, chatRoomId);  
    validateNotBlocked(senderId, opponent.getId());  
    return sender;  
}
```

이런 요구사항에 많은 변경점이 요구되는 것을 보면 결국 코드 설계 측면에서 잘못된게 아닐까라는 생각이 들었다.  

위 메서드는 여러 책임을 갖고 있다.  

- 채팅멤버를 조회
- 상대방 조회
- 차단 여부 검증

```java
private ChatRoomMember validateCanSendMessage(Long chatRoomId, Long senderId) {
    // 1. 발신자의 채팅방 참여 정보 조회
    ChatRoomMember sender =
            chatRoomMemberService.findActiveMemberByRoomIdAndMemberId(chatRoomId, senderId);

    // 2. 상대방 조회
    Member opponent =
            chatRoomMemberService.findPartnerMember(sender, chatRoomId);

    // 3. 메시지 전송 가능 여부 검증
    validateNotBlocked(senderId, opponent.getId());

    // 상대방은 버리고 발신자만 반환
    return sender;
}
```

여러 책임을 가질 뿐만 아니라 검증 메서드에서 새로운 데이터를 조회하며 이를 반환하지 않아 데이터가 유실된다. 심지어 해당 메서드는 QueryDSL로 호출하기에 캐싱조차 되지 않는다.

- `private` 메서드 내부적으로 데이터를 `select`하는건 피해야 할까?
- `select`는 하되 리턴한다면 전혀 문제가 없을듯 하다.

```
- 해당 채팅방 멤버 전부 조회 (현재 1:1 채팅방만 있기에 부담 없음)
- auth로 받은 id를 기준으로 상대와 나를 구분
```

위와 같이 설계했다면 `select` 2번을 1번으로 줄일 수 있을거 같다.

## 엔티티의 `@AllArgsConstructor을 지양

- 엔티티는 기본 생성자 필요 (`@NoArgsConstructor`)

> JPA는 리플렉션이나 프록시를 통해 엔티티를 생성하기 위해 `public` 또는 `protected` 기본 생성자를 요구한다.  

- `@Builder` 사용시 모든 인자를 받는 생성자를 생성함
	- 그러나 생성자가 있을 경우 생성하지 않음
	- 즉, 기본 생성자를 만들었다면 에러 발생
- 그렇기에 `@AllArgsConstructor`를 명시

이렇기에 대부분의 엔티티들은 아래와 같이 롬복 어노테이션을 관습적으로 붙인다.  

```java
@Getter  
@Builder  
@AllArgsConstructor  
@NoArgsConstructor
public class Member extends BaseEntity { }
```

여기서 주의할 점은 엔티티에 풀 생성자가 있는 것이다.  
아래와 같이 같은 타입이 여러개 있다면 문제 발생 가능성이 있다.  

```java
public Member(String name, Integer age, String address) {
	this.name = name;
	this.age = age;
	this.address = address;
}

// 잘못된 생성자 사용이지만 에러가 아님
new Member("서울시 강남구", 26, "홍길동");
```
