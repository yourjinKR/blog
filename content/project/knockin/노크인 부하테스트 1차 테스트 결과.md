## 단일 조회부터 안정화

부하 테스트시 DB 환경을 어떻게 구축할지 고민했다. 일단 1차적으로 내린 결론은 기존의 H2 방식으로 진행하되 운영 환경인 PostgreSQL과는 다른 환경임을 인지하고 개발을 진행하기로 했다.  

```properties
seed.load-test.records-per-entity=10000
```

위와 같이 설정하여 기존에 있던 `SeedDataConfig` 클래스에 반복문으로 동일한 임시 데이터를 삽입하는 방식으로 진행했다.   

그러나 게시물이 10,000건일때 TimeOut이 발생했다.  
TimeOut 설정이 5초이기에 단일 조회 자체가 5초 소모된다는 것이기에 우선 단일 조회 자체 성능부터 안정화 할 필요가 있다.

시드데이터 10,000건 이상부터 타임아웃이 발생했기에 설정을 아래와 같이 다시 설정

결론  
→ 적절한 시드 데이터의 사이즈를 정하는게 우선이라고 생각  
→ 아래 지표를 측정하기 위해 서버를 on/off를 반복하면서 nGrinder UI를 통해 반복 실행 및 복붙을 반복함. 이를 좀 자동화 할 수 있는 방법을 고민

우선 아래와 같이 스크립트를 구성

- 특정 시드 데이터 크기로 서버 실행
- nGrinder에 등록된 모든 스크립트들을 각각 N번씩 실행 (이때 각 응답-요청이 겹치치 않는게 좋다면 그렇게 설정)
- 실행결과 수집 후 기록

결과는 TPS 10 이하에서도 에러가 발생하는 처참한 성능을 확인했다.  

![[IMG-20260928220202319.png]]

일단 부하 테스트 환경에는 대표적으로 다음과 같은 문제가 있다.  

- H2 사용으로 CPU 및 메모리를 크게 점유
- 서버, nGrinder, 외부 다른 작업까지 동시에 수행

우선 재현 환경을 통일 시키고 좀 더 일관성 있는 지표가 필요할거 같다.
